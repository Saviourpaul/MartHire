# Workable Integration — Design

Date: 2026-10-24
Status: Draft, awaiting approval
Supersedes: `2026-10-24-greenhouse-integration-design.md` (provider pivot Greenhouse → Workable). The Greenhouse design and its committed Tasks 1–3 are superseded history on this branch, not merged.
Grounding: Workable API reference (workable.readme.io), fetched 2026-10-24 — endpoints, auth, and payload shapes in §2 are copied from the live docs; where a real payload disagrees with this doc, the real payload wins.

## Intent and why
Make Marthire a Workable-backed job board with a full candidate journey: sync an employer's **published** Workable jobs into our DB, show them on public list/detail pages, let registered candidates apply through a native form we build from Workable's application-form schema and submit server-side (create-candidate) with the account's token, and fall back to the job's hosted Workable application URL when native apply can't be guaranteed. The browser never talks to Workable; the account token never leaves the server. Submission is at-most-once with human-resolved ambiguity (a duplicate application harms the employer relationship more than a rare manual resubmit).

## Scope
Full journey (user-chosen 2026-10-24): jobs + candidate accounts + apply. Build order still phases the demo floor first (see §12). Out of scope: Workable employees/talent-pool/webhooks/candidate-management endpoints; anything beyond reading jobs and creating candidates.

## What carries over from the (superseded) Greenhouse design
Architecture and process are unchanged: thin controllers → actions → a single owned `WorkableClient` → DTOs/typed exceptions → Eloquent models + queued jobs; raw API arrays never cross the client boundary; **approach A** credential storage (encrypted token per account in the DB, never `.env`); idempotent queued sync with guards; the apply **outbox / at-most-once state machine**; security/privacy rules (encrypted secret, `$hidden`, log scrubbing, HTML sanitize at render, private file disk, data minimization/purge, consent); CI never touches the live API (fixtures + `Http::fake`).

## The provider pivot — what changes vs Greenhouse (the important part)
1. **Auth:** `Authorization: Bearer <token>` (not HTTP Basic). One **account token** with scopes (`r_jobs` to read jobs/questions/form, `w_candidates` to apply). Token is secret.
2. **Everything is authenticated.** Even listing jobs needs the token server-side. So the Greenhouse premise "public board GETs; the whole site works with zero credentials" is gone: with no account configured there are simply no jobs to show (the platform still runs; apply is redirect-only). This is a deliberate, documented change.
3. **Base URL is per-account:** `https://{subdomain}.workable.com/spi/v3`. The client builds it from the account's `subdomain`; config holds only the host template/version, not a fixed base URL.
4. **Jobs are keyed by `shortcode`** (a string) for all sub-resource and apply calls; there is also an opaque `id`. We store both; URLs/questions/form/apply all use `shortcode`.
5. **Workable DOES validate** required fields and returns `422` with `validation_errors` (e.g. duplicate email keyed under `email`). We still validate server-side for UX, and still map `422` → a permanent `PayloadRejected`, surfacing field errors (duplicate email → a friendly "already applied" message).
6. **Apply = create-candidate**, not a form POST of `question_{id}` fields. Answers are an `answers[]` array keyed by `question_key` with type-specific value fields; resume is base64 `{name,data}` or `resume_url`.

## §2 Ground truth (from the live docs, 2026-10-24)
- **List jobs:** `GET /spi/v3/jobs` (scope `r_jobs`). Query: `state` (`draft|published|archived|closed` — use `state=published`), `limit` (default 50, **max 100**), `since_id`, `max_id`, `created_after`, `updated_after`, `include_fields` (adds `description`, `full_description`, `requirements`, `benefits`). **Pagination:** response `paging.next` is a full URL to the next page — follow it; sorted oldest-first by insertion time. Job fields: `id`, `title`, `full_title`, `shortcode`, `code`, `state`, `confidential`, `department`, `department_hierarchy[]`, `url`, `application_url`, `shortlink`, `workplace_type`, `location{...}`, `locations[]`, `created_at`, `updated_at`, `keywords[]`, `salary{salary_from,salary_to,salary_currency}`. Descriptions only present with `include_fields`.
- **Job detail:** `GET /spi/v3/jobs/{shortcode}` (scope `r_jobs`).
- **Application form:** `GET /spi/v3/jobs/{shortcode}/application_form` (scope `r_jobs`). Returns `{ form_fields[], questions[] }`. `form_fields[]`: `key`, `label`, `type` (`string|free_text|file|boolean|date|complex`), `required`, `fields[]` (when `complex`), `supported_file_types`/`max_file_size` (when `file`). `questions[]`: `id`, `body`, `type` (`free_text|multiple_choice|boolean|dropdown|numeric|date|file`), `required`, `single_answer` (multiple_choice), `choices[]{id,body}` (multiple_choice|dropdown), `supported_file_types`/`max_file_size` (file). Standard fields (name/email/phone/resume/cover_letter/address/summary/headline) appear in `form_fields` with their own `required` flags; name/email/phone presence not fully documented — confirm from the live form.
- **Create candidate (apply):** `POST /spi/v3/jobs/{shortcode}/candidates` (scope `w_candidates`). Body: `sourced` (set **`false`** so it's an applied candidate), `candidate{ email (req), name OR firstname+lastname (req), phone?, cover_letter?, summary?, address?, headline?, skills[]?, tags[]?, domain?, education_entries[]?, experience_entries[]?, social_profiles[]?, answers[]?, resume{name,data(base64)} | resume_url }`. `answers[]` = `{ question_key, + one of: body (free_text/short_text ≤128) | checked (boolean) | choices[] (choice ids) | date | value (numeric) | file{name,data}|file_url }`. Success `201 {status:"created", candidate:{...}}`. Errors: `401 {"error":"Not authorized"}`, `404 {"error":"Not found"}`, `422 {validation_errors}`.
- **Unverified (confirm from the pilot account + capture as fixtures):** exact rate limits and whether `429`/`Retry-After` is returned (assume yes, stay conservative); the precise `paging.next` interaction with `since_id`; the full `form_fields` standard-field set and which are on by default; whether `short_text` is a real `questions` type (seen in examples). Capture live fixtures once the subdomain + token are in.

## §4 Data model (deltas from Greenhouse)
- `companies`: `id`, `name`, `slug` (unique), **`subdomain` (unique)**, **`api_token`** (text, nullable, `encrypted` cast, `$hidden`), `scopes` (json nullable), `apply_mode` enum `native|redirect` default `redirect`, `credentials_status` enum `unverified|valid|invalid` default `unverified`, `last_synced_at`, timestamps.
- `job_postings`: `id`, `company_id` FK, **`shortcode`** (string — the Workable sub-resource/apply key), `external_id` (string — Workable `id`), `title`, `full_title` (nullable), `state` (string), `department` (nullable), `workplace_type` (nullable), `url`/`application_url`/`shortlink` (nullable), `location` (json), `locations` (json), `salary` (json nullable), `keywords` (json), `content_html` (longtext nullable; built from description/full_description/requirements/benefits), `content_hash`, `external_updated_at`, `status` enum `open|closed`, `last_seen_at`, `closed_at`, `apply_supported` (nullable bool). unique `(company_id, shortcode)`; index `(status, external_updated_at)`. Mapping: `state=published` → `open`; disappeared/`archived|closed|draft` → `closed` (keep URL; serve "no longer accepting applications").
- `job_applications`: `id`, `job_posting_id` FK, `idempotency_key` (uuid unique), `email`, `first_name`, `last_name`, `status` (queued|submitting|submitted|failed_*|needs_review), `attempts`, `error_code` (nullable), `payload` (encrypted array cast — answers + file refs until purged), `schema_hash`, `workable_candidate_id` (nullable), `http_status` (nullable), `response_excerpt` (nullable, PII-free), `consent_version`, `consented_at`, `submitted_at`, timestamps. unique `(job_posting_id, email)`.
- `sync_runs`: unchanged from Greenhouse (`company_id`, started/finished, status `ok|failed|suspicious`, fetched/created/updated/closed ints, error nullable).

## §5 WorkableClient (public contract)
- `listPublishedJobs(Company $c): Collection` // JobPostData[], follows `paging.next`, `state=published&limit=100&include_fields=...`
- `getJob(Company $c, string $shortcode): JobPostData`
- `getApplicationForm(Company $c, string $shortcode): ApplicationSchema`
- `createCandidate(Company $c, string $shortcode, array $payload): SubmissionResult`
- Bearer auth from the account token; base URL built from `subdomain`; 5s connect / 15s total timeouts; GETs retry 3× on connection/429/5xx; POST never retries in the client. Error mapping: 401/403→`CredentialsRejected`, 404→`JobNotFound`, 429→`RateLimited(retryAfter)`, 422→`PayloadRejected(validationErrors)`, connection-before-send / 5xx GET→`TransientFailure`, read-timeout / 5xx after POST→`AmbiguousOutcome`. Never log the token, the `Authorization` header, or POST bodies/responses.

## §6–§9 Sync / Apply / Security / Reliability
Same shapes and rules as the Greenhouse design (idempotent sync with empty/failed-fetch guards and sweep-only-after-success; lazy application-form resolution cached 15 min; server-side validation from the schema; outbox at-most-once with the §7.5 state machine — `AmbiguousOutcome`→`needs_review`, no auto-retry; encrypted token hidden+scrubbed; sanitize `content_html` at render; private file disk; purge on success + retention; consent recorded; structured logs with IDs only; `workable:health`; `FAKE` mode serving fixtures). Apply differences: build the form from `application_form` (`form_fields` + `questions`); submit via create-candidate with `sourced:false`; map `422 validation_errors` to form field errors (duplicate email → "you've already applied"); fallback link is the job's `application_url`/`shortlink`.

## Decisions / codebase deltas
1. Namespace `App\Integrations\Workable` (new). The superseded Greenhouse files (`config/greenhouse.php`, `App\Integrations\Greenhouse\*`, `tests/Fixtures/greenhouse/*`, Greenhouse tests) are removed in the first Workable task — non-destructive (they remain in branch history). *Ruling: supersede, don't hard-reset — keeps history, matches "not merged".*
2. DB queue + cache (no Redis); build list/detail/apply/status pages on the Marthire design system (`build-frontend.mjs`). *My call.*
3. **Auth-registration fix is now a prerequisite (finding #1).** Full journey needs working candidate accounts; registration is currently broken (users table has only `name`; model/controller write nonexistent `firstName`/`lastName`). The first functional task fixes it: migration for `first_name`/`last_name`, align model/validation/controller, fix the 2 known-red tests (`RegistrationTest`, `ProfileTest`).
4. Config `config/workable.php`: `api_version` (`v3`), `host_template` (`https://%s.workable.com/spi/%s`), `user_agent`, `fake` (bool), `sync_empty_guard_min_open` (5), `schema_cache_minutes` (15), `application.max_file_mb` (5), `application.payload_retention_days` (30). Subdomain + token are per-company (DB), never env.

## §12 Build order (phased)
- **W0 Foundation + fixtures + auth fix:** config; typed exceptions; representative Workable fixtures (jobs list, job detail, application_form, create-candidate success + 422); DTOs; **registration/auth fix** (unblocks accounts). *Done when: DTO tests pass against fixtures; registration + profile tests green.*
- **W1 Client + sync:** `WorkableClient` (list with pagination, getJob, getApplicationForm, createCandidate) with `Http::fake` tests + error mapping; encrypted-token `Company`; `JobPosting`/`SyncRun`; `SyncCompanyJobs`; `workable:add-company`; `workable:sync` + schedule. *Done when: fixtures ingest; idempotent second run; disappeared job → closed; empty/failed-fetch guards proven.*
- **W2 Public site:** list/search/filter/detail pages on the design system; sanitized content; JSON-LD JobPosting; redirect-apply on every job. *Done when: site renders jobs; XSS test passes; works with redirect-only.*
- **W3 Native apply:** application-form resolution + dynamic form + server validation + outbox + queued create-candidate + state machine + emails; 422/duplicate handling; redirect fallback. *Done when: a labelled test application lands in the pilot Workable account and they confirm+delete; duplicate blocked; worker-kill mid-flight loses nothing.*
- **W4 Hardening:** throttles, purge job, alerts, `workable:health`, requeue. *Done when: revoked-token drill flips company to redirect + alerts ops + candidate gets hosted link.*
- **W5 Demo polish:** `WORKABLE_FAKE` mode, seed, README. *Done when: full demo runs offline from fixtures.*
